Playwright Standard Framework — Interview Guide

From scratch explanation · Architecture · Design decisions · Interview Q&A · Commands

1. What is Playwright & Why a Framework?

Playwright (Microsoft) automates Chromium, Firefox, WebKit and can also call APIs.

Raw scripts work for 2–3 tests, but fail at scale (copied selectors, hardcoded passwords, mixed envs, no CI). A framework = structure + rules + reusable layers so the team writes tests the same way.

4. Folder Guide

playwright.config.ts

  • Projects: chromium, firefox, webkit, api, utils
  • CI retries, screenshots/video/trace on failure
  • baseURL from env; reporters: list, HTML, JUnit, Allure
  • ENV=local starts dummy-app via webServer

config/ — Multi-environment

Files: qa|staging|prod|local.env.json + env.config.ts. Contains baseUrl, apiBaseUrl, timeouts, DB, feature flags.

Switch: npm run test:qa / test:staging / test:local. Secrets override via .env / CI (DB_*).

Add new env: copy JSON + users → update EnvironmentName → add npm script.

data/users/ — Credentials

Keys like standard, locked, apiAdmin. Tests use fixtures / getUser('standard') — never hardcode passwords in specs.

pages/ — Page Object Model

FileRole
base.page.tsShared click/fill/navigate/wait
login.page.tsLogin
inventory.page.tsProducts / cart badge
cart.page.tsCart
checkout-*.page.tsCheckout flow

Bad: selectors inside specs. Good: await loginPage.login(user.username, user.password).

Why POM: reuse, one fix when UI changes, tests read like business steps.

api/ — API layer

base.api.ts (GET/POST/PUT/PATCH/DELETE) → users.api.ts (ReqRes), products.api.ts (local dummy).

fixtures/test.fixture.ts

Extends Playwright test so every spec gets loginPage, usersApi, standardUser, etc. injected automatically (DRY setup).

tests/

tests/ui browser · tests/api REST · Arrange → Act → Assert. Tags: @smoke, @ui, @api.

utils/

ExcelUtil, DbUtil (MySQL), DateUtil, StringUtil, FileUtil, WaitUtil, AssertUtil. Prefer Playwright auto-wait over hard sleeps.

dummy-app/ + practice apps

  • Local shop + /api at http://127.0.0.1:4173 (ENV=local)
  • UI remote: Sauce Demo · API remote: ReqRes

CI / Reports / Cursor

  • CI: GitHub Actions, GitLab (.gitlab-ci.yml), Jenkins, Azure
  • Reports: HTML, JUnit, Allure
  • .cursor/: rules + skills + MCP (Jira Atlassian + Playwright browser) for ticket → POM tests

5. One UI Test Flow (Explain Aloud)

  1. ENV=qa loads qa.env.json → baseUrl = Sauce Demo
  2. Fixture creates LoginPage, InventoryPage, standardUser
  3. Test: open → login → expectLoaded
  4. On failure: screenshot / video / trace
  5. Result goes to HTML / Allure / JUnit

6. Design Points Interviewers Love (Memorize)

  1. Separation of concerns (pages / api / tests / config / utils)
  2. POM — no selectors in specs
  3. Multi-env via JSON + ENV
  4. Externalized users/data
  5. UI + API in one repo
  6. Custom fixtures
  7. Stable locators (data-test, role, label)
  8. CI-friendly (retries, artifacts)
  9. Reporting (HTML + Allure + JUnit)
  10. Secrets via env/CI — not committed for real systems
  11. Scalable — add page/API/env without rewrite
  12. Maintainable — UI change → fix one page class

7. Two-Minute Interview Script

“I built a Playwright TypeScript automation framework for UI and API testing.

UI uses Page Object Model—page classes hold locators and actions; tests call business methods only.

API wraps Playwright’s request context in clients like UsersApi.

Config is environment-driven: QA, staging, prod, local JSON files for URLs, timeouts, DB—selected by ENV. Users live in separate JSON per environment.

Custom fixtures inject pages, API clients, and users. Utils cover Excel, MySQL, dates, and random data.

It integrates with GitHub Actions, GitLab, Jenkins, and Azure; publishes HTML/JUnit/Allure reports; and includes a local dummy app. We also added Cursor rules/skills so Jira MCP + Playwright MCP generate POM tests following the same standards.”

8. Common Q&A

Q. Why Playwright over Selenium?
Auto-wait, multi-browser, tracing, API in same tool, parallel workers, modern selectors, often less flaky.

Q. What is POM?
UI in page classes; tests describe behavior. One place to fix when UI changes.

Q. Multiple environments?
ENV loads config/<env>.env.json; users from data/users; CI passes ENV.

Q. Test data?
User JSON, Excel/JSON under data/, StringUtil for unique values, optional DbUtil.

Q. Reduce flakiness?
Auto-wait, no fixed sleeps, stable locators, CI retries, traces, isolated data, no order dependency.

Q. UI vs API?
Same repo. UI → pages + browser projects. API → api/ + api project (no browser). Shared config/fixtures.

Q. What is a fixture?
Playwright setup injection. We extend test so loginPage / usersApi / standardUser are ready.

Q. CI/CD?
Install Node + browsers, set ENV/CI, run projects, publish artifacts.

Q. Smoke only?
npx playwright test --grep @smoke

Q. Locator changed?
Update page object only; specs keep working.

Q. Debug failures?
HTML report, screenshot/video, --debug, trace viewer, headed mode.

Q. Add a new page?
New page class → register fixture → new spec under tests/ui.

9. Commands to Remember

npm install
npx playwright install

npm test                 # QA default
npm run test:ui          # UI chromium
npm run test:api         # API
npm run test:local       # local dummy app
npm run test:headed
npm run test:debug
npm run report           # Playwright HTML
npm run allure:report    # Allure (needs Java)
